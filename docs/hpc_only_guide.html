DART does not submit Slurm jobs or move files. It generates the scripts, tracks the record, and parses the outcome. Every submission and every file transfer is your responsibility.

Navigating to the HPC pipeline

In the sidebar, under Data movement pipeline, select HPC. You will see the HPC Transfer page with four tabs.

Tab 1 New transfer

Open this tab when a new RT ticket comes in. Fill in the details and create the database record. Nothing is written to disk at this point — it is purely a record that gives the transfer a unique ID used throughout the rest of the process.

FieldDescription
RT ticket numberThe RT ticket number for this request
Artifact nameShort identifier for what is being moved, e.g. imagenet-val
Requester usernameShaheen3 username of the person who raised the ticket
Typedataset, model, software, or other
Source pathFull path to the artifact on cpup
Destination pathFull path to the destination on gpup
Size (GB)Approximate size — for record-keeping only
NotesAny context about the transfer

Click Create transfer record. A workspace directory is created at:

/scratch/project/k03/support_team/workspace/<ticket>_<name>/

Note the transfer ID shown in the success message — you will need it in Post-move.

Tab 2 Pre-move

Generate a checksum of all files at the source before touching any data. This is the reference fingerprint. After the data is moved, the checksum is verified at the destination — if every file matches, the transfer is confirmed clean.

steps
1
Select the transfer
Pick the transfer from the dropdown. Ticket, artifact name, and source path are filled automatically.
2
Generate the script
Click Generate & save pre-move script. The dashboard writes generate_checksum.slurm to the workspace. The checksum file will be written inside the source directory — the path is shown in the info box.
3
Submit the script at the source
The sbatch command is shown after generation. Run it in your terminal:
sbatch /scratch/project/k03/support_team/workspace/<ticket>_<name>/generate_checksum.slurm
Monitor the job:
tail -f /scratch/project/k03/support_team/workspace/<ticket>_<name>/logs/checksum_generate_<JOBID>.log
4
Move the data
Once the checksum job completes, transfer the data. The checksum file is inside the source directory and travels with the data automatically.
rsync -avP /source/path/ /destination/path/
ℹ
The checksum uses relative paths so it remains valid wherever the data lands. checksum.sha256 and artifact.yml are excluded from the checksum automatically.

Tab 3 Post-move

Verify that every file arrived intact at the destination. This tab has two steps — generating the verify script and importing the result.

Step 1 — Generate verification script

1
Select the transfer
Pick the same transfer from the dropdown. Ticket, name, and destination path are filled automatically.
2
Generate the script
Click Generate & save verify script. The dashboard writes verify_checksum.slurm to the workspace. The result file path is shown — it will be written to the workspace once the job completes.
3
Submit the script
Submit from anywhere — the script uses absolute paths:
sbatch /scratch/project/k03/support_team/workspace/<ticket>_<name>/verify_checksum.slurm
Monitor:
tail -f /scratch/project/k03/support_team/workspace/<ticket>_<name>/logs/checksum_verify_<JOBID>.log
The job writes a summary to the log and verify_result.txt to the workspace.

Step 2 — Import verification result

Once the verification job completes, return to the Post-move tab.

The Transfer ID and result file path are pre-filled. Click Import result & complete record. DART parses the result, records the pass/fail counts, and marks the transfer:

✓
All files OK → transfer marked completed
⚠
Any failures → transfer marked anomaly — do not close the ticket yet

Handling anomalies

If the transfer is marked anomaly:

1
Check which files failed
grep "FAILED" /scratch/project/k03/support_team/workspace/<ticket>_<name>/verify_result.txt
2
Re-rsync the failed files
rsync -avP /source/path/failed_file /destination/path/
3
Regenerate and resubmit the verify script
Go back to Post-move Step 1, regenerate the script, resubmit, then import the new result.

Tab 4 Transfer log

Shows all transfers with status, ticket, artifact name, type, and operator. Use the search box to filter by ticket number and the dropdown to filter by status.

Click Detail on any row to open the detail view.

Detail view

The detail view has five sections:

SectionWhat it shows / does
Edit recordAll fields are editable. Shows a sync warning if an edited field affects an already-generated script — directing you to regenerate it from the Pre-move or Post-move tab.
Verification resultTotal, passed, and failed file counts from the last verification run. Only visible after a result has been imported.
Modification logEvery action from the workspace YML — actor, timestamp, action, note.
Audit log (DB)Every database-level event — status changes, field edits.
Update statusManually set any status with an optional note. Use this for in-progress or blocked.
⚠
Editing after scripts are generated — if you change source_path, destination_path, ticket_number, or artifact_name after a script has been written, a warning appears. Go to the Pre-move or Post-move tab, select the transfer, and regenerate the affected script. The old script is overwritten.
